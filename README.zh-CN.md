# 流式纠纷调解辅助模型 · 长对话实时案件状态跟踪

[English](README.md) | **简体中文**

在**纠纷调解对话进行的过程中**，模型逐轮增量地维护并输出案件的结构化状态——各方**诉求 / 已认定事实 / 争议焦点 / 证据 / 调解方案**——辅助调解员边谈边理清案情，而不是等调解结束才一次性总结。

---

## 一、项目在解决什么

社区调解员在调解过程中，需要随着双方对话的推进，实时梳理五类信息——各方**诉求**、已认定**事实**、**争议焦点**、**证据**，以及可能的**调解方案**，据此辅助调解工作。

项目最初采用"调解结束后、依据完整笔录一次性生成案件摘要与结构化信息"的做法。但随着业务推进发现，这种**事后总结**模式无法满足真实场景：调解员真正需要的，是在调解**进行过程中持续更新案件状态**，而不是事后拿到一份总结报告。

因此系统被升级为面向**长对话场景的流式状态跟踪框架**——每推进若干轮对话，就输出一份"当前时点的案件全量状态"，让调解员边谈边看、状态随谈随变。这也是整个项目最大的挑战。

相比一次性生成，流式生成需要额外解决两个全新问题：

- **信息不足时保持留空(Abstention)**：对话里没出现的事实、金额、证据，模型必须留空，绝不能凭空补充——宁可空着，不可编造。
- **持续维护状态、而非每轮重写**：每轮对话后，模型要在已有信息上**准确更新变化的部分**，同时保持整场调解的状态一致性，而不是把全量重新生成一遍。

这意味着模型不仅要理解当前输入，还要在整场调解中保持状态的连续与自洽。

---

## 二、输入 / 输出

模型**按轮增量工作**：每一步吃「**上一轮累积的五要素全量态 + 本轮新对话**」，只吐「本轮变化(diff)」，完整状态由程序在步间滚动回灌。

**输入**（每一步喂给模型的）：
- 本轮**新增的对话**（自上一份快照以来新说的话，带轮次、说话人、角色）；
- **名册**（谁是申请人 / 被申请人 / 调解员，真名对应）；
- 到目前为止**已累积的案件状态**（全量五要素）。

**输出**：截止当前这一步的**案件状态快照**——五要素，每个要素下再带结构化子字段：

| 要素 | 关键子字段(举要) |
|---|---|
| 诉求 | 编号、诉求内容、当前状态(新提出 / 协商中 / 接受 / 拒绝…)、来源对话 |
| 已认定事实 | 编号、事实描述、当前状态(一方待回应 / 双方确认 / 争议中…)、各方态度(谁认可 / 否认 / 未回应) |
| 争议焦点 | 编号、争议问题、当前状态、关联的诉求 / 事实、还缺什么信息 |
| 证据 | 编号、证据内容、提交状态(已提及未上传 / 已提交 / 已核对…) |
| 调解方案 | 方案内容、待确认事项、各方态度、当前状态，以及**策略话术**——按**情 / 利 / 理 / 法**四个维度组织的分步话术建议，外加"禁止说的话、要观察什么、何时切换策略" |

> 字段完整清单、取值词表与一个可运行的合成示例，见 [`docs/数据格式_输入输出_纯格式版.md`](docs/数据格式_输入输出_纯格式版.md)。

## 三、架构

流式状态跟踪的核心 = **程序维护全量 + 模型只写变化**。

### 核心：增量式(Diff)流式生成

不让模型每轮重发整份状态（会带来重复生成、历史丢失、甚至把已确认内容结构性删掉）。改为：

```
程序侧  维护【完整累积状态】   —— 确定性累加，不依赖模型
模型侧  只生成【本轮的变化】   —— 新增 / 更新 / 新的调解方案
未变化的项 → 程序自动带入下一份快照
```

- 状态能**持续累积更新**；
- "擅自删除历史"在**结构上不可能**——模型没有"删"这个动作，只能新增或更新；
- 模型每步输入有界、输出小而干净。

### 程序侧(封装层)做什么

把模型吐的"本步 diff"落成"可用的当前全量状态"，是**封装层**的职责，全程确定性、不依赖模型：

1. **累加**：本步 diff 合并进已维护的全量态——新增项追加、更新项就地改字段、未变项原样保留。
2. **去重 / 空更新过滤**：模型偶尔把"没有实质变化"的项也重发；封装层比对新旧值，**值没变就丢弃**，不让它污染状态或制造无意义的反复改写。
3. **一致性回归**：每步累加后校验结构不变量（状态词有没有越界、编号是否自洽、有没有引用未来轮次、有效项有没有被丢），不过就拦下。

一句话：**模型负责理解与变化，程序负责状态与纪律**——模型不必背全量、也无从破坏历史，结构正确由程序兜底。

## 四、数据与模型的评测指标

评测分两层：先量**数据**够不够干净（训练前预检 + 交付前自查），再量**模型输出**好不好。

### 4.1 数据质量指标(训练前达标才开训)

| 指标 | 定义 | 合格线 |
|---|---|---|
| 无编造率(Grounding) | 每条要素都能在对话里指到出处 | 抽检 ≈ 100% / 编造 ≈ 0 |
| 归属准确率 | 每条态度归到真正说这句话的人 | 抽检 ≈ 100% |
| 状态词表闭合率 | 状态机字段取值 ∈ 闭合词表 | 100% |
| 未来信息泄漏率 | 每条来源轮次 ≤ 本快照 cutoff | 0 |
| 擅删率 | 仍有效的项在后续快照中丢失 | 0 |
| 编号自洽率 | 同事同号、不裂号、按前缀顺延 | 100% |
| 算术自洽 | 金额加减、分期折价前后对得上 | 0 错 |

> 结构类（词表 / 泄漏 / 擅删 / 编号）靠规则查死→硬门槛必须清零；语义类（编造 / 归属）是难点→抽检逼近 0、发现即修。

### 4.2 模型输出评测指标

| 维度 | 指标 | 怎么判 |
|---|---|---|
| 结构合规 | 状态词表闭合、编号自洽、无泄漏、无擅删 | 规则可自动判，应 ≈100% / 0 |
| 状态跟踪 | 状态一致率(模型态 vs 金标一致)、覆盖率(该带的项都带上) | 逐项比对 |
| Grounding | 无编造率(输出无对话外信息) | 回指来源核 |
| 方案 / 话术质量 | 好率 / 差率(方案与话术是否扣本案事实、有无空话套话) | 多评委打分 |
| 归属准确率 | 态度未张冠李戴、无塌合键 | 回指来源核 |
| 生成稳定性 | 无重复退化(diff 不陷入 loop) | 规则 + 人工 |

> **判定方法（LLM-as-judge · 多评委交叉评审）**：评委团选自 **Opus 4.7 / 4.8、Fable 5、Opus 5、GPT 5.6** 等不同家族模型，每轮**三评委独立打分、≥2 票共识**才采信——单评委容易过报，跨家族交叉能压低误判。

### 4.3 一个结论

**格式不是瓶颈，语义纪律才是**：规范的 diff，裸基座光凭 system prompt 就能产出；微调真正买到的，是"不编造、不擅删、不塌合归属、状态词收敛"这套**语义纪律**。

## 五、部署 / 使用

本仓可两种用法：**只要 adapter**（拿到基座热挂 LoRA，diff→全量态的累加逻辑自行实现），或**直接用随仓发布的封装层**（`serving/`，即 §三「程序侧」的生产实现）。

### 前置依赖（公开仓无法内置，需自备）

1. **基座模型 `Qwen3.6-35B-A3B`**（MoE，架构 `qwen3_5_moe`，~35B 总参 / ~3B 激活）：非公开可下载；adapter 只能挂在该 base 上，并需 transformers / vLLM 支持该架构。
2. adapter 权重 `adapters/v4g/adapter_model.safetensors`（~172 MiB）经 **Git LFS** 分发——clone 后请确认已装 `git lfs` 且拉到的是真实权重而非 LFS 指针文件。
3. 封装层依赖 `fastapi` / `uvicorn` / `requests`。

**起完整封装层**（§三「程序侧」的生产实现：后端 vLLM + FastAPI 归一服务）：

```bash
# 后端 8000(base + LoRA) + 封装 8001
MEDIATION_API_KEY=<你的token> BASE_MODEL=/path/to/Qwen3.6-35B-A3B TP=4 \
  bash serving/start_lora_v4g.sh
```

契约：`POST /api/mediation/generate` {当事人, 新对话, 当前累积状态?} → {code, message, data, diff}。

## 六、仓库结构

本仓以 **adapter + 封装层 + 推理 demo + 文档** 为主；数据，以及数据生成 / 清洗 / 质检 / 门禁 / 评测 / 训练等工程脚本不随仓发布（涉及内部配方与真实数据）。系统提示词随仓发布（`prompts/`，推理必须使用）。

```
stream-mediation-agent/
├── README.md                          ← 英文版（仓库首页）
├── README.zh-CN.md                    ← 本文件
├── prompts/
│   ├── system_cprime_procfilter_v4.txt ← 封装层默认
│   └── system_v4g.txt                 ← v4g adapter 训练时那份（train==serve 单一事实源）
├── adapters/
│   └── v4g/                           ← v4g LoRA 适配器（不 merge，热挂 serve）
│       ├── adapter_config.json
│       ├── adapter_model.safetensors  ← ~172 MiB，Git LFS 分发
│       └── README.md                  ← provenance（基座 / 超参 / best ckpt）
├── serve/
│   ├── serve_vllm_lora.sh             ← 裸 vLLM 起 base + LoRA（参数化）
│   └── demo_infer.py                  ← 极简推理 demo（纯标准库，内置合成案）
├── serving/                           ← 生产封装层（§三「程序侧」的完整实现）
│   ├── app_stream_v4g.py              ← FastAPI 服务：POST /api/mediation/generate
│   ├── conv_prompts_stream_v4g.py     ← system/user 组装；SYS_FILE 切换 prompts/
│   ├── normalize_diff_v4g.py          ← diff 归一：累加 / 去空更新 / 描述锚定 / 硬规则过滤 / 灰区判官
│   └── start_lora_v4g.sh              ← 一键起 后端 vLLM + 封装层
└── docs/
    ├── 数据格式_输入输出_纯格式版.md    ← 字段 schema + 取值词表 + 回灌循环 + 合成示例
    ├── diff走查示例.md                 ← 一条案例逐步 diff 走查
```

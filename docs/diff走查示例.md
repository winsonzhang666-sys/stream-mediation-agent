# v4 流式 diff — 一条完整案例走查（**合成示例** · 物业费纠纷）

> ⚠️ **本文为演示 diff 机制而虚构的合成案例**：当事人 `张三 / 李四` 均为占位名，金额为整数演示值（物业费 4000 元、九折 3600 元、车位费 50 元/月等），情节亦为杜撰，**与任何真实案件无关**。真实训练数据依法保密、不入库；此处仅用于讲清"模型每步只吐变化、全量由程序累积"的机制。

> **案件（虚构）**：物业费纠纷 · 张三（物业方/申请人）vs 李四（业主/被申请人）。整段对话切成 **4 个流式步**。

> **看什么**：每一步的 **输入**（名册 + 当前累积状态 + 新对话）→ 模型 **输出**（diff）→ 程序 **应用 diff 后的全量累积态**。重点体会：模型每步只吐「变化」，全量由程序累积、没变的项程序自动带走。

```

turn_002 调解员: 面积、单价、欠费月数和总数4000元，李四那边都认，没异议；你们从2021年3月开始服务也确认。我先核实一个事——你们跟小区签的前期物业合同，是2020年1月1日签、2023年12月31日到期，对吧？

turn_006 调解员: 我先听听李四本人最在意哪几条，回头再来跟你谈。
```

## 这条走查说明了什么

1. **模型每步只吐个位数 diff**，全量态（这里最终 11 条）由程序按 `claim_/fact_/issue_/evidence_` 前缀确定性累积——「擅删」在结构上不可能发生。
2. **落定 = 改「当前状态」，不是删项**：`claim_002` 走「拒绝→协商中→已解决」，一路留痕可回溯。
3. **归属分人、沉默不臆测**：`fact_002` 李四全程「未回应」就一直记「未回应」，`fact_005` 是李四本人说的、张三确认后才转「双方确认」。
4. **状态词取自闭合词表**（对方尚未回应/协商中/部分接受/已谈拢/已解决…，态度取 认可/否认/部分认可/未回应，提交状态取 已提及未上传/已提交/已核对），不是每步换个说法——这套受控口径正是微调买到的东西。

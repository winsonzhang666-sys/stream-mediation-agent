# 流式调解模型 · 输入 / 输出格式规范（纯格式版）

> 只讲数据**长什么样**，不含任何生成 / 处理 / 质量要求。
> 模型**按轮增量工作**：每一步只吃「上一步累积出的全量状态 + 本轮新对话」，只吐「本轮的变化（diff）」；完整状态由外层程序在步与步之间滚动维护。

---

## 一、总览：每一步的输入 / 输出 + 回灌循环

| | 是什么 |
|---|---|
| **每步输入** | 名册 ＋ **上一步累积出的全量状态**（五块 JSON；首步为空）＋ 本轮新增对话 |
| **每步输出** | 本轮 **diff**（只含这轮新增 / 更新的要素 ＋ 当前调解方案；没变的要素不重复输出） |

```
第 t 步：
  输入 = 【当事人】名册
       + 【当前累积状态】（全量五块 JSON；首步为 “(空，这是第一步)”）
       + 【新对话】（本轮新增的几轮）
        │
        ▼  模型
  输出 = 本轮 diff  { 新增, 更新, 调解方案 }
        │
        ▼  外层程序：把 diff 累加进【当前累积状态】
  得到第 t 步的全量状态  ──►  作为第 t+1 步的【当前累积状态】
```

**五要素** = 诉求 / 事实（已认定事实）/ 争议焦点 / 证据 / 调解方案。
**编号前缀约定**：`claim_`＝诉求、`fact_`＝事实、`issue_`＝争议焦点、`evidence_`＝证据；同一件事跨步**用同一个编号**。

---

## 二、输入：三个纯文本块

模型每一步收到三段纯文本：

### 2.1 `【当事人】` 名册
一行，分号隔开：`姓名(方) ; 姓名(方)`
例：`张三(申请人方) ; 某物业公司(被申请人方)`

### 2.2 `【当前累积状态】` 全量五块（上一步累加出的）
一个 JSON，含全部五要素的当前全量状态；结构与输出里的要素**完全一致**（见 §三）。
**首步为空**——字面就是一行 `(空，这是第一步)`。

### 2.3 `【新对话】` 本轮新增对话
每行一轮：`turn_编号 说话人: 文本`
例：
```
turn_007 某物业公司: 灯我们一周内修好，修好后欠的2400能不能三天内补上？
turn_008 张三: 只要灯真修好，我三天内补2400。
```

---

## 三、输出：本轮 diff

一个 JSON，含以下键：

| 键 | 出现时机 | 含义 |
|---|---|---|
| `新增` | **有才给** | 数组。本轮**首次出现**的要素（诉求/事实/争议/证据），整条给出；编号在该类型当前最大号上顺延 |
| `更新` | **有才给** | 数组。累积状态里**已有、这轮变了**的要素，整条重发（**含原编号，编号不变**）；撤回/解决/放弃 = 把 `当前状态` 改成对应词放进这里，**不删除** |
| `调解方案` | **每步必给** | 对象（单例，无编号）。整块输出，反映当前方案 ＋ 这一步「怎么谈」的策略话术 |

> 没变的要素一律**不输出**，外层程序会从累积状态自动带走。`新增`/`更新` 数组里各类要素**靠编号前缀区分**：`claim_`=诉求、`fact_`=事实、`issue_`=争议、`evidence_`=证据。

### 各要素结构（与累积状态里一致）

```
诉求      {编号, 诉求, 当前状态}
事实      {编号, 描述, 当前状态, 方态:{姓名:态度}}
争议焦点  {编号, 问题, 当前状态, 还缺什么信息:[...]}      # 还缺什么信息，无则省略该键
证据      {编号, 证据, 提交状态}
调解方案  {内容, 待确认事项:[...], 当前状态,
          策略话术:{当前障碍, 策略目标, 话术建议:[{维度, 参考话术}]}}
```

- **事实 · 方态**：是「姓名 → 态度」的字典，**一人一条**；在场但没表态的人**不列**。
- **调解方案 · 内容**：还没有具体方案时**留空**。
- **策略话术 · 话术建议 · 维度**：取 **情 / 利 / 理 / 法** 其一（情理服人、利害说明、法理依据、事理厘清）。

---

## 四、6 个状态机字段的闭合词表（逐字照用，出范围即错）

自由文本字段（诉求`诉求`、事实`描述`、争议`问题`、证据`证据`、方案`内容`）照对话如实写、没有就留空；下面 6 个**状态机字段只能从词表里选一个词**，不许自造、不许改写、不许往词里塞细节。

| 字段 | 允许取值（只能选其一） |
|---|---|
| 诉求 · 当前状态 | 新提出 / 对方尚未回应 / 协商中 / 对方提出反方案 / 条件接受 / 部分接受 / 接受 / 已谈拢 / 拒绝 / 已撤回 / 已放弃 / 未解决 |
| 事实 · 当前状态 | 一方说了待回应 / 双方确认 / 部分认可 / 对方否认 / 待材料核实 / 争议中 / 已更正 / 已撤回 |
| 事实 · 方态 · 态度 | 认可 / 部分认可 / 否认 / 主张 / 未回应 |
| 争议焦点 · 当前状态 | 争议中 / 范围缩小 / 暂时共识 / 部分共识 / 重新争议 / 已解决 / 搁置 |
| 证据 · 提交状态 | 已提及未上传 / 已提交 / 已核对 / 无法提交 |
| 调解方案 · 当前状态 | 内部草案 / 已提出 / 部分达成 / 达成一致 / 失效 / 中止 |

> 状态词只表达「到了哪一步」；**谁、多少钱、什么条件**等细节写进同项的自由文本字段（描述/诉求/问题/证据/内容），**绝不塞进状态词**。

## 五、最小完整示例（合成案例，与真实案件无关）

**输入（某个中间步，第 t 步）：**
```
【当事人】张三(申请人方) ; 某物业公司(被申请人方)

【当前累积状态】
{"诉求":[{"编号":"claim_001","诉求":"张三要求先修好楼道灯再补交物业费","当前状态":"对方提出反方案"}],
 "事实":[{"编号":"fact_001","描述":"张三近两年未缴物业费，共2400元","当前状态":"双方确认","方态":{"张三":"认可","某物业公司":"认可"}}],
 "争议焦点":[{"编号":"issue_001","问题":"是否应先修好楼道灯再补缴物业费","当前状态":"争议中","还缺什么信息":["楼道灯损坏的责任与时间"]}],
 "证据":[{"编号":"evidence_001","证据":"某物业公司提供的欠费明细，用以证明欠费2400元","提交状态":"已提及未上传"}],
 "调解方案":{"内容":"","待确认事项":[],"当前状态":"内部草案",
  "策略话术":{"当前障碍":"双方卡在先修还是先补","策略目标":"用限期修缮换补缴承诺",
   "话术建议":[{"维度":"利","参考话术":"灯一周修好，修好你再补，不吃亏。"}]}}}

【新对话】
turn_007 某物业公司: 灯我们一周内修好。修好之后，欠的2400能不能三天内补上？
turn_008 张三: 只要灯真修好，我三天内补2400，没问题。
turn_009 调解员: 那就这么定：物业一周内修好楼道灯，张三在修好后三天内补缴2400元，再定个验收方式。
```

**输出（本轮 diff）：**
```json
{
  "新增": [
    {"编号":"issue_002","问题":"楼道灯维修完成如何验收确认","当前状态":"争议中","还缺什么信息":["双方认可的验收方式"]}
  ],
  "更新": [
    {"编号":"claim_001","诉求":"张三要求先修好楼道灯再补交物业费","当前状态":"已谈拢"},
    {"编号":"issue_001","问题":"是否应先修好楼道灯再补缴物业费","当前状态":"已解决","还缺什么信息":[]}
  ],
  "调解方案": {
    "内容":"物业一周内修好楼道灯，张三于灯修好后3日内补缴2400元",
    "待确认事项":["维修完成的验收方式"],
    "当前状态":"达成一致",
    "策略话术":{"当前障碍":"验收方式尚未定","策略目标":"敲定验收方式、固化时间节点",
     "话术建议":[{"维度":"理","参考话术":"把『一周修好、修好三天内补』写清楚，再约个验收，双方都安心。"}]}
  }
}
```

> 外层程序把这份 diff 累加进【当前累积状态】：`issue_002` 追加，`claim_001`/`issue_001` 就地改，`调解方案` 整块替换，`fact_001`/`evidence_001` 未变、原样保留 → 得到第 t 步全量态，作为第 t+1 步输入。
>
> **首步**：`【当前累积状态】` 为 `(空，这是第一步)`，此时所有要素都进 `新增`，`调解方案` 照常给出（内容可留空、先给策略话术）。
